The 8 parts of every OpMode top to bottom, every time

1package org.firstinspires.ftc.teamcode;

2import com.qualcomm.robotcore.eventloop.opmode.LinearOpMode;
import com.qualcomm.robotcore.eventloop.opmode.TeleOp;

3@TeleOp(name = "Main TeleOp")
4public class MainTeleOp extends LinearOpMode {

5    // one Robot object, built once, shared by every method
    private final Robot robot = new Robot();

6    @Override
    public void runOpMode() {
        robot.init(hardwareMap);
        waitForStart();          // nothing moves before START

7        // one pass, about 50 times a second, until STOP
        while (opModeIsActive()) {
            double speed = 1.0;
            if (gamepad1.left_bumper) {
                speed = 0.4;     // slow mode while held
            }
            robot.drive(-gamepad1.left_stick_y * speed,
                         gamepad1.left_stick_x * speed,
                         gamepad1.right_stick_x * speed);

            if (gamepad2.rightBumperWasPressed()) {
                robot.launcherOn();   // once per press
            }
8            telemetry.addData("Heading", "%.1f deg",
                    robot.headingDegrees());
            telemetry.update();
        }
        robot.stopDrive();
    }
}

What each part does

1package: the folder this file lives in. Line 1 of every file, always the same. 2imports: addresses of classes from other packages. Alt+Enter writes them for you. 3annotation: puts the OpMode on the Driver Hub list under that name. AUTO uses @Autonomous. 4class: the blueprint. Same name as the file. extends = gets telemetry, gamepad1, hardwareMap for free. 5field: a box the whole class shares. One Robot object serves every method. 6runOpMode: the SDK's blank spot, filled in by you. Set up, then wait for START. 7the loop: read the sticks, decide, move, show, repeat. Never sleep here. 8telemetry: lines for the Driver Hub screen. No update(), no screen.

Who does what

Robot.java knows the motor names and the wheel math. Private parts, public actions. One per robot.

An OpMode has a Robot and decides: read the gamepad, call an action, show telemetry.

PIDController.java turns an error into power. One class for the turn, the lift and auto-aim.

If a line names a motor and the file is not Robot.java, the line is in the wrong file.

Words you will see the ones the lab uses on every tab

public any file can use it. Actions like drive().
private only this class can use it. Motors stay private.
static belongs to the class, not one object: Math.abs(x).
final set once, never changed. A constant when on a number.
MAX_SPEED UPPER_CASE = a tuned constant, changed in one place.
new Robot() builds one object from the blueprint.
this.kP the box in this object. Plain kP: the number passed in.
Robot() no return type = the constructor. Runs once, inside new.
void the method hands nothing back. Call it as its own line.
double boolean a decimal, or true/false. Before a name: what it hands back.
return hands the value back and ends the method right there.
(double a, double b) parameters: the inputs, filled in order by the caller.
enum a type with a short fixed list of values. A typo fails the build.
switch case break jump to the matching case. Forget break: it runs on.
if else && run when true, else the other block. && = both true.
while (opModeIsActive()) repeat until STOP. One pass = one loop.
hardwareMap.get(DcMotor.class, "name") which kind, and the exact config name.
-gamepad1.left_stick_y stick up reads negative. The minus fixes it.
left_bumper true while held. rightBumperWasPressed() true once per press.
Range.clip(x, -1, 1) keeps x inside the limits. Power stays in -1 to 1.
"%.1f" a decimal with 1 digit after the point, for telemetry.
ElapsedTime a stopwatch object. seconds() and reset().
// a comment. Say why, not what.
; { } end of a statement. A block, and the life of its variables.

1One loop, no sleep

sleep(1000) freezes the loop: motors keep the last power and nobody can steer for a second.

A state machine checks one thing per pass and moves on. Driving keeps working while the launcher spins up.

enum LaunchState {
  IDLE, SPINNING_UP, FEEDING
}

switch (launchState) {
  case IDLE:
    if (gamepad2.rightBumperWasPressed()) {
      robot.launcherOn();
      launchState = LaunchState.SPINNING_UP;
    }
    break;
  case SPINNING_UP:
    if (robot.launcherReady()) {
      launchState = LaunchState.FEEDING;
    }
    break;
  case FEEDING:
    robot.feedOnce();
    launchState = LaunchState.IDLE;
    break;
}

Timing without sleep: if (timer.seconds() > 0.5) inside the loop. Threads move the robot before START (rule G304.H).

2Open loop vs closed loop

setPower(0.8) is open loop: 80% of whatever the battery gives. 13.6 V at the start, 11.8 V at the end, so late shots fall short.

setVelocity(1160) is closed loop: the encoder measures the speed and the hub adds power until the wheel hits 1160 ticks/s, on any battery. Sensor, target, correction, every pass.

Shoot only when launcherReady() is true: within 40 ticks/s of the target.

3Drive modes

Robot-centric: stick up = the robot's front. Turn the robot and "up" turns with it.

Field-centric: stick up = away from the driver wall, whatever the robot faces. The IMU heading rotates the stick before the wheel math.

Same mecanum math underneath: fl = axial + lateral + yaw, scaled so no wheel passes 1.0.

4PID: error in, power out

P kP * error. Big error, big push. Alone it stops short when friction or gravity eats the small push. Too much: overshoot and wobble.

I kI * (error added up). Supplies the missing push when P stalls short. Only near the target (the I-zone). Too much: slow wind-up.

D kD * (how fast the error changes). The brake near the target. Too much: jitter on a noisy sensor.

Tune on the robot: kP until it overshoots a little. Then kD until the overshoot stops. Then a small kI only if it stops short. Test 5 times, then commit the numbers.

Rise time 10% to 90% of the way Overshoot past the target, in % Settling time in the band, and stays Steady-state error the offset at the end

One class, every sensor: IMU for a turn, encoder for the lift, camera for auto-aim. Camera data is late and noisy, so PD beats PID there.

7Before you open a pull request

  • Builds without errors
  • No threads, no sleep in TeleOp
  • Hardware lives in Robot.java only
  • Hardware names match the robot config
  • Robot does not move between INIT and START
  • Tuned numbers are named constants
  • Telemetry shows the values I expected
  • AI box ticked if AI helped, and what for
  • I explain every line to my reviewer. "The AI wrote it" is not an answer
