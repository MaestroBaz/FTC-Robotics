    Robot.java: public and private
    
              
    private: only code inside the same class can use it. public: any class can use it. Our rule: motors and sensors are private inside Robot.java. Actions like drive() are public.
    
              
    Why: if only Robot.java touches the motors, every wheel power goes through the same math. Nobody in an OpMode can set one wheel to full power by mistake.

    extends and @Override
    
              
    extends means "is a kind of". MainTeleOp extends LinearOpMode says: MainTeleOp is a kind of LinearOpMode. It gets everything LinearOpMode has, and LinearOpMode gets everything OpMode has. That is why telemetry, gamepad1 and waitForStart() work without you creating them.
    
              
    @Override means "replace the parent's version with mine". LinearOpMode has a method called runOpMode() with nothing inside. When the driver presses INIT, the SDK calls runOpMode(). You write your own runOpMode(), and the SDK runs yours.
    
              
    The @ line is a note to the compiler: "check that the parent really has a method with this exact name". A typo then fails the build on your laptop, not the robot on the field. Try it below.
    
              
    Team rule: extend LinearOpMode, and stop there. No chains like RedAuto extends BaseAuto extends LinearOpMode. Share code with one Robot object instead: a TeleOp has a Robot.

    Four mistakes that compile, or almost
    
              
    
                
    if (balls = 3)
    One = stores a value. Two == compare. Build error: incompatible types: int cannot be converted to boolean. Fix: if (balls == 3)
    
                
    if (alliance == "RED")
    For text, == asks "same object?", not "same letters?". It compiles and gives wrong answers. Fix: alliance.equals("RED")
    
                
    if (power == 0.3)
    Decimal math rounds a tiny bit: 0.1 + 0.2 is 0.30000000000000004. Ask "close enough" instead. Fix: Math.abs(power - 0.3) < 0.01
    
                
    if (stick > 0.05) ... else if (stick > 0.5)
    The order matters. 0.8 passes the first test, so the second never runs. Fix: put the strictest test first.

    Both launchers fire POLLEN at the HIVE. Orange uses setPower(0.8). Blue uses setVelocity(1160), which reads the encoder and corrects. Drag the battery voltage or run a whole match.
    
    
    
    
    Ask the roomA fresh battery reads 13.6 V. By the end of a match it reads 11.8 V. What happens to a launcher set to setPower(0.8)?Teams hold up A, B or C. Click what each team holds up, Team 1 first. Right-click takes the last vote back. Reveal pays a point to every team that got it right.
    Reveal answer    
      
    Power is a fraction of battery voltage. Lower voltage means a slower wheel, so shots fall short late in the match. setVelocity() measures the speed with the encoder and adds power until the wheel reaches the target. This is the "external feedback" the Control Award asks for. Inside the hub, setVelocity() runs PIDF. F comes first: the hub knows 1160 ticks/s needs about 0.8 power, so F sends that power before any error shows. A correction from the encoder error fixes the rest, like the dip after a shot or a low battery. Tab 7 names the correction: P, I and D.

    PID control: one class, every sensor
    
      
    A PID controller turns an error (how far you are from the target) into motor power. P pushes toward the target, D brakes before you overshoot, I fixes what is left over. Pick a job below: the PID code stays the same. Only the sensor, the error and the 3 numbers change. The lift adds a 4th number, kF: power you send before any error shows, because gravity always pulls.
    
    
    
    
    Ask the roomThe lift holds 2 inches below its target and never gets there, even though kP is set. Which term fixes this, and why does P alone fail?Teams hold up A, B or C. Click what each team holds up, Team 1 first. Right-click takes the last vote back. Reveal pays a point to every team that got it right.
    Reveal answer    
      
    Gravity needs about 0.18 power to hold the lift still. With P only, the motor gets that power only from an error: error x kP = 0.18. So the lift stops where the error makes exactly 0.18, below the target. I adds up the leftover error over time until the power reaches 0.18. I is the answer. Now pick the lift job and watch the shortcut: F adds the 0.18 from the first loop pass, before any error.
    
    
    
  
    
  
    
    
    
    
  
    
  
    
    
    The control loop numbers update live. The brighter a term box, the harder it pushes.
    
    
    
    
      
    I: the integral is the area under the error
    
      
    D: the derivative is the slope of the error
    
    
    
  
    
  
    
    
    
      
    
        
    Turn to heading
    
        
    
        
    
        
    
          
          
          
        
    
        
    
        
    
      
    
      
    
        
    How to tune trial and error, in this order
    
        
      
          
    1. Lift or arm only: find F first. Set kP, kI and kD to 0. Raise kF until the lift holds still wherever you leave it. That number cancels gravity.
      2. 
          
    2. Set kI and kD to 0. Raise kP until the robot reaches the target fast and overshoots a little.
      3. 
          
    3. Raise kD until the overshoot and wobble stop. Too much D makes the motion slow and jittery.
      4. 
          
    4. If it still stops short (friction, a heavier load), add a small kI and watch the I line grow on the chart. The class builds I only near the target, so I cannot pile up during a long move and push past the target (windup).
      5. 
          
    5. Test 5 times in a row. Write the numbers in Robot.java and commit with what you tested.
      6. 
        
    
      
    
      
    
        
    The class you reuse PIDController.java: P, I and D from the error. F needs no error, so you add F in the OpMode
